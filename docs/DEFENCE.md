# Defending the earthquake catalog design

| Decision | Explain in an interview | Hard follow-up and reconsideration trigger |
|---|---|---|
| [Integrated scope](adr/0001-catalog-structure.md) | The same interrupted backfill gives an analyst a reference comparison and an operator old and new publication IDs. | Can a reviewer do this offline in one run? Revisit scope if the review exceeds the time budget. |
| [Independent acquisition](adr/0002-catalog-acquisition.md) | Freeze two query paths, compare duplicate counts before deduplication, and keep the live and restart verdicts separate. | What if USGS revises an event between queries? Preserve both bodies and withhold publication. Shrink the period if the whole-window reference exceeds the service limit. |
| [Transactional publication](adr/0003-catalog-storage.md) | Commit rows with their checkpoint. Each reader must digest the rows it actually receives and match its named generation. | Can the old ID still be read after recovery? Reconsider SQLite if multiple writers or measured reader stalls invalidate the design. |

**How do you know the older ID still works?** In M05 a fresh CLI process retrieved the earlier ID after the pointer advanced. The drill compared each returned row to the whole-week reference filtered to 1–3 October and recomputed the same digest observed before the switch. Returning the latest rows for both IDs would fail on count and membership. The larger count reflects four additional days of coverage. M06 added a separate oracle per ID, computed from the whole-week response. Hashing actual returned rows caught the controlled old-rows/new-label fault. A read spanning commit can legitimately see either complete ID. Fresh reads after confirmed commit must see the new one. [Publisher incident](postmortems/m06-publisher-crash.md). [History drill](evidence/M05-history.txt)

**What does four readers establish?** The CLI starts a Python process for each read. Four overlapping loops completed 96 timed reads and increased aggregate throughput to 12.73/s, with a pooled p95 of 335.77 ms. A different reader interface or a longer run may behave differently. The 125.22 MiB figure sums sampled resident working sets; peaks between polls are unknown. The first orphan drill found a redundant download. The repaired acquisition reused all 1,839,817 whole-response bytes after a process kill. [Remediation](evidence/M07-orphan-remediation.txt).
